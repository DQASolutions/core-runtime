# @dqa-ai-solutions/ontology-base

The ontology's declarations and nothing else. No I/O, no dependencies. Every engine that reads an
ontology takes its types from here.

| Part | What |
|---|---|
| `src/` (→ `dist/`) | TypeScript declarations: value types, entity and relationship types, shared concepts, behaviour signatures (actions, functions, rule results, events) |
| `schema/ontology-file.schema.json` · `.yaml` | The ontology **file** format, as JSON Schema (draft-07). The two files hold the same schema |
| `conformance/cases.yaml` | Language-neutral cases: files, and what a validator (`schema`) and an engine (`kernel`) must say about them |

## Ontology files: YAML or JSON

An ontology is one or more files, merged in order. Each file is a mapping with any of `valueTypes`,
`entities` and `relationships`. Write it in YAML (`.yaml`, `.yml`) or in JSON (`.json`). JSON is YAML,
so one parser reads both, and an empty file is an empty mapping.

```yaml
# yaml-language-server: $schema=node_modules/@dqa-ai-solutions/ontology-base/schema/ontology-file.schema.json
valueTypes:
  - { name: money, type: number, minimum: 0, multipleOf: 0.01 }
entities:
  - name: Order
    label: Order
    properties:
      - { name: amount, type: number, valueType: money }
relationships: []
```

The first line lets a YAML editor check the file as you type.

A project may add its own keys anywhere. An engine that does not understand a key ignores it.

## Two levels of checking

- **`schema`** is what JSON Schema can say about one file:
  - names are safe identifiers;
  - property types are known;
  - an `enum` has values and a `catalogue` names its collection;
  - each constraint keyword is used only on the types it applies to, and is written in the right form;
  - no provenance field (`id`, `source_ref`, `confirmed_by`, `confirmed_at`) is declared.
- **`kernel`** adds what needs the whole set of files:
  - an entity or relationship name is declared once across all files;
  - a property is declared once;
  - relationship ends name declared entities;
  - every `valueType` resolves and matches its property's type;
  - a lower bound is not above its upper bound;
  - a `pattern` compiles the way a browser compiles it.

`cases.yaml` marks every case at both levels. It covers both formats, files spread across formats,
anchors and comments, an empty file, and project keys. In this repository:

- `npm test` here runs the cases against the schema, and checks that the JSON and YAML schema files
  still match their generator.
- `@dqa-ai-solutions/ontology-loader`'s `conformance.test.ts` runs the same cases against the kernel.

An engine in another language conforms when it gives the same `kernel` verdict on every case.

The schema is generated by `scripts/build-schema.mjs` (`npm run schema`). Edit the generator, not the
two schema files.
